# Test plan and results

All numbers below come from test runs executed during this build (Java 21, Linux amd64, 2 CPUs, a local Docker daemon, PostgreSQL 16 in Docker). Nothing here was estimated.

## Strategy

| Level | Scope | Where |
|---|---|---|
| Unit | tokenizers, normalization, hashing, winnowing, index, Dice, GST; judge comparator, classifier, adapters, orchestration with a fake container runner; storage; ZIP extractor; UI labels and line marking | `engine/src/test`, `judge/src/test`, `backend/src/test/.../storage`, `frontend/src/frontend.test.tsx` |
| Integration (real containers) | every verdict, resource limit and sandbox restriction against real Docker | `JudgeDockerIT` |
| Integration/acceptance (real DB + HTTP) | full API scenario on PostgreSQL with the real worker and judge | `AcceptanceTest` |
| Measurement | precision/recall/FPR on a labelled synthetic set; scale benchmark | `QualityMeasurementTest`, `BenchmarkTest` |
| Manual/ad hoc | Playwright (Chromium) walk-through of instructor and student UI against the live app; viewport overflow measurement | not checked in as a suite |

Docker/DB-dependent tests use JUnit Assumptions: on a machine without Docker they are **skipped, not passed**. They ran here.

Commands: `mvn test` (needs Docker, the four runner images and PostgreSQL; set `POSTGRES_PASSWORD`, test DB `codesentinel_test`), `cd frontend && npm test`.

## Judge sandbox coverage (JudgeDockerIT, 22 tests)

AC in C, C++, Java, Python, JavaScript; WA; CRLF/trailing-whitespace accepted; CE in C, Java, Python; RE by exit code and by segfault; TLE (infinite loop, returned in <60 s); MLE (allocation loop, via Docker OOM flag); fork bomb contained (not AC, not IE); output flood bounded; network blocked; source mount and root FS read-only; non-root, no `docker.sock`, `/etc/shadow` unreadable; hidden test input not present in the container filesystem; Java without `main` → CE; unsupported language → IE.

## Acceptance scenario (AcceptanceTest, 13 tests)

Login/401/lockout (429 after 5 failures); course + assignment + hidden tests + reference file; student registration only with a valid code; **student JSON contains no hidden test name/input/expected output and no reference file**; draft assignment invisible; other instructor gets 404; hostile uploads (traversal ZIP, `.exe`, NUL bytes, wrong language, bad name) rejected; real AC and WA judged by the worker with hidden detail null for the student; cross-student reads 404; plagiarism run on 6 synthetic Python solutions; students 403 on pair endpoints; review validated and **carried over a re-run**; wording check (no "guilty/cheat/plagiarised…"); dashboards computed from data; audit actions present and no password/token text in audit details.

Result of the plagiarism scenario: the planted renamed/reordered copy surfaced as `NEEDS_REVIEW` with score 0.783 (below the 0.80 high-priority threshold); the four independent solutions produced no candidate pair.

## Plagiarism quality (SYNTHETIC dataset)

Source: `docs/results/engine-quality-report.md` (generated by `QualityMeasurementTest`). 17 submissions = 12 independent solutions (several implement the same textbook algorithms) + 5 deliberate copies (exact, renamed+commented, reformatted, padded, reordered+renamed) → 136 pairs: 5 positive, 131 negative.

Default configuration (`FIRST_OCCURRENCE_UNIT`, starter suppression on, cutoff 0.30), positive = `NEEDS_REVIEW` or `HIGH_PRIORITY_REVIEW`:

| | Predicted positive | Predicted negative |
|---|---|---|
| Actual copy | TP = 5 | FN = 0 |
| Actual independent | FP = 0 | TN = 131 |

Precision 1.000, recall 1.000, FPR 0.000. Counting only `HIGH_PRIORITY_REVIEW`: TP 4, FP 0, FN 1 (the padded copy is `NEEDS_REVIEW`, score 0.68).

Ablation (same file): with the stricter whole-file identifier numbering, recall fell to 0.60 (3/5); disabling starter suppression lowered high-priority recall. This is why the defaults differ from the first draft of the spec (see IMPLEMENTATION_LOG.md).

**How to read this honestly.** The copies were written by the same author who built the detector, and the "independent" programs are few and short. These figures show the pipeline behaves as designed on constructed cases; they are **not** evidence of accuracy on real student work, and they do not support any claim of "zero false positives" in general. Validation on real, instructor-labelled submissions (or a public corpus) was not done.

## Performance (synthetic)

From `docs/results/engine-benchmark.txt`: 100 submissions × ~314 lines.
- Realistic (diverse) workload: best of 3 = **599 ms**; 3 candidate pairs of 4,950; 3 flagged (the 3 planted copies).
- Homogeneous worst case (every program built from the same template): **3,376 ms**; 4,948 candidate pairs; 0 flagged.
Target < 5,000 ms met on this 2-CPU machine in both. Not a guarantee elsewhere. Judge latency was not benchmarked separately; for scale, the 22 Docker tests (each a compile + run, several waiting for a timeout) took 17.3 s in total.

## Frontend

`tsc -b` clean, `vite build` succeeds (≈207 kB JS, 64 kB gzip). Ad hoc Chromium run: no console errors; student cannot see hidden test text, is redirected from instructor routes, gets "Not found" on another student's submission. `document.documentElement.scrollWidth` equals the viewport at 420 px on 8 pages after a CSS fix (it overflowed before; found by screenshot).

## Not tested / known gaps

- No real symlink ZIP; no MIME sniffing. (Past-deadline, retry/recovery, archive and export tests were added after the first report; totals above are from a full re-run on 2026-11-09.)
- No load test of the HTTP API; no concurrency test of two workers claiming jobs (the SQL uses `FOR UPDATE SKIP LOCKED`; one worker was exercised, and web + worker processes were run separately once).
- No automated accessibility audit; no cross-browser testing (Chromium only, ad hoc).
- No security penetration test. Container isolation relies on Docker defaults plus the flags listed; it is not a hardened (gVisor/Firecracker) sandbox.
